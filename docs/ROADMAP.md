# V2 구현 로드맵

## Phase 0 — 인수인계와 프로젝트 기준선

상태: 완료

- V1.5 조사 문서와 안전 표본 이전
- 목표 구조, 개발 원칙, 결정사항 기록
- 비밀값과 로컬 생성물을 제외하는 규칙 추가

완료 기준: 새 작업에서 V1.5 대화를 다시 읽지 않아도 V2의 목적과 다음 작업을 이해할 수 있다.

## Phase 1 — 로컬 개발 환경과 DB 연결

상태: 완료

- Python 가상환경 및 패키지 구성
- PostgreSQL Docker Compose 구성
- 환경변수 예시와 설정 로더
- DB 연결 확인용 최소 코드와 테스트

완료 기준: 새 환경에서 문서의 명령만으로 PostgreSQL을 실행하고 Python 연결 테스트를 통과한다.

## Phase 2 — 수집 공통 기반

상태: 완료

- HTTP client와 명시적 timeout
- 제한된 동시성, 재시도, 지수 backoff와 jitter
- 구조화 로그와 `run_id`
- 응답 redaction과 schema fingerprint

완료 기준: 성공, 404, 429, 5xx, 잘못된 JSON을 테스트로 재현하고 각각 안전하게 분류한다.

## Phase 3 — 목록 1개 구간 수집

상태: 완료

- 목록 응답 모델과 검색 조건 builder
- PostgreSQL migration: `crawl_runs`, `crawl_requests`, `vehicle_listings`
- 표본 fixture 기반 파싱 테스트
- 실제 API는 1~20건 canary만 실행

완료 기준: 개인정보 없이 목록을 저장하고, 같은 응답을 다시 처리해도 중복 행이 생기지 않는다.

## Phase 4 — 실제 차량 ID 해석

상태: canary 완료 — 다양한 유형 표본 검증은 Phase 6에서 계속

- 축약 상세 호출
- `vehicles`와 광고 alias 연결
- ORIGINAL/DUPLICATION 사례 테스트
- 미해석·404·재시도 상태 관리

완료 기준: 여러 광고 ID가 같은 실제 차량을 가리킬 때 차량은 하나, 광고는 여러 개로 저장된다.

## Phase 5 — 상세 데이터 확장

상태: 진행 중 — 통합 옵션 코드·메타데이터·보험이력·차량번호 저장 완료, 성능·진단은 미구현

- 옵션 카탈로그와 차량 옵션
- 보험 이력과 사고 상세
- 성능 점검과 외판 부위
- 엔카 진단과 사진
- 개인정보 제거 snapshot

완료 기준: 각 endpoint가 독립적으로 실패해도 이미 수집한 차량과 다른 endpoint 데이터가 손상되지 않는다.

## Phase 6 — 500~1,000대 canary

- 국산·수입·화물·승합·전기차 표본
- null, 404, 중복, 미등록 옵션 코드 통계
- 요청 속도와 실패율 관찰
- 중단 후 재시작 및 실패 복구 검증

완료 기준: 허용 기준을 수치로 기록하고 재실행해 같은 결과를 재현한다.

## Phase 7 — 제조사 단위와 최초 전체 수집

- 제조사 또는 작은 facet 단위 shard
- 기대 Count와 고유 광고 수 검증
- staging 적재 후 검증된 결과만 merge
- 한 제조사 전체 수집 후 전체 약 20만 대로 확대

완료 기준: 일부 shard 실패가 성공한 shard와 기존 데이터에 영향을 주지 않고, 실패 구간만 다시 실행할 수 있다.

## Phase 8 — 일일 갱신

- 신규 광고와 목록 fingerprint 변경 감지
- `last_seen_at`, `missing_streak`, 판매 종료 판정
- 활성 차량의 분산 심층 재검사
- 수집 실행 현황과 이상 감지

완료 기준: 일시적 0건·누락·응답 변경으로 기존 매물이 대량 종료되지 않는다.

## Phase 9 — 서비스 연결

- Spring Boot 검색 API
- 검색 projection과 실제 조회 기반 인덱스
- React 프론트엔드 연결

완료 기준: 프론트엔드는 저장 구조를 알지 않고 하나의 검색 API만 사용한다.
