# V2 결정사항

## 확정

| 항목 | 결정 | 이유 |
|---|---|---|
| 저장소 | V1, V1.5와 분리된 V2 저장소 | 원본 보존과 독립 배포 |
| 초기 언어 | Python 3.14 | 2030년까지 지원되는 안정 버전이며 주요 라이브러리가 지원 |
| 데이터베이스 | PostgreSQL 18.6 | 현재 지원되는 최신 안정 메이저와 패치 버전 |
| 초기 Docker 범위 | PostgreSQL만 | Python 학습·디버깅 복잡도 감소 |
| 데이터 모델 | 판매목록 한 건을 통합 `vehicles` 한 행으로 저장 | 현재 매물 검색에 불필요한 중복·조인 제거 |
| 식별자 | 판매 매물 ID를 `vehicles` 기본키로 사용 | 상세 조회와 현재 목록 갱신의 직접 기준 |
| 옵션 | 메타데이터 카탈로그 + 차량별 통합 코드 배열 | 불필요한 그룹과 수백만 연결 행 없이 다중 조건 검색 |
| 갱신 | 목록 fingerprint + 주기적 상세 재검사 | 목록만으로 상세 변경을 모두 알 수 없음 |
| 삭제 정책 | 연속 누락과 상태 확인 후 비활성화 | 일시적 오류에 의한 데이터 손상 방지 |
| 차량번호 | `vehicles.vehicle_no`에 직접 저장 | 구매 판단에 필요하고 별도 테이블의 실익이 작음 |
| 개인정보 | VIN·연락처·주소·판매자 설명 원문 미저장 | 최소 수집과 노출 위험 축소 |
| 이미지 | 파일과 URL 모두 초기 수집에서 제외 | 이용허락 전 복제·재전송 위험을 줄임 |
| 서비스 API | 추후 Spring Boot | 수집기와 사용자 API 책임 분리 |

## 구현 전에 재검증

- 목록 API에서 `inav` 생략 가능 여부
- `cursor` 기반 페이징 동작
- 500건 요청의 실제 반환 수와 중복률
- 보험 API의 `vehicleNo` 생략 가능 범위
- 개인정보 객체를 제외하면서 필요한 상세만 받는 `include` 조합
- 충분히 낮은 속도에서 장시간 호출 안정성
- 내부 API 자동 수집에 관한 이용 조건과 허용 범위

## 아직 결정하지 않음

- Python 수집기의 최종 Docker 배포 시점과 방식
- 운영 환경과 배포 제공자
- 스케줄러와 작업 큐
- Spring Boot/React의 구체 버전과 배포 형태
- 검색 projection을 materialized view로 할지 별도 테이블로 할지

결정되지 않은 항목은 현재 단계의 코드를 불필요하게 고정하지 않는 방향으로 둔다.
